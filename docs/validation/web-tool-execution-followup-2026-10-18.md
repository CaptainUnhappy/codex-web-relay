# 后续计划：工具执行与会话退出

状态：已记录证据，尚未启动实现。

## 目标

让 Web 发送的工具任务能完成或明确报错，显示真实工具状态，并在用户归还后可靠释放会话。保留单会话限制、结果未知不重放、运行或审批期间不自动中断的约束。

## 已知事实与未知项

- 公网登录、缓存列表、纯文本发送、回复后 60.9 秒自动归还和独立原生客户端接回已通过。测试使用 CLI 0.159.0。
- 受控命令仅为 `Write-Output 'relay-tool-ok'`，由 code-mode `exec` 调用 `tools.exec_command`。持续等待同一个 cell 超过四分钟，没有取得命令结果，也没有待审批项。
- 原生持久记录含 `custom_tool_call: exec` 及多次 `function_call: wait`；对应 `thread/items/list` 没有工具项。需确认是协议表达缺失、事件订阅、版本兼容，还是后端转换的问题。
- `stop` 返回 200，随后归还超时；Mini 诚实保留 releasing 状态，没有假报释放成功，但读取随之被阻止。
- 命令执行挂起和退出等待的具体原因均未确认，不能仅靠增加超时、隐藏错误或强制清空 ownership 处理。
- 后续只读补测已观察到当前桌面会话的工具摘要在公网 Web 从 9 条增长到 16 条，包含命令、文件编辑、MCP 和协作任务，页面实际渲染成功。故问题不是所有桌面工具都无法同步；仍需定位缺失的具体工具表达与先前受控任务的执行/退出阻塞，详见 `web-session-handoff-2026-10-18.md` 的最新补测。

## 执行顺序

1. 在隔离测试会话中复现固定字符串命令，记录从 code-mode 到命令执行器的请求、确认和退出边界。比较直接原生命令与 code-mode 调用，确认阻塞点；不改变用户审批或沙箱策略。
2. 比较原生通知、`thread/items/list` 和持久工具记录。依据实际支持的协议恢复工具名称与状态，只公开必要的进度信息，不输出内部推理或凭据。
3. 修复已定位的执行或退出问题。保留正常 EOF 退出；异常退出处理必须验证当前所有者及进程归属，不能按进程名笼统终止，也不能在未确认退出时清空占用状态。
4. 用真实受控工具任务重测公网发送、工具状态、停止、手动归还、空闲归还和另一客户端接回。最后恢复 60 秒设置、归档测试对话、记录证据并仅本地提交。

## 验收条件

- 固定字符串命令在明确的 30 秒测试窗口内返回结果或可解释的失败/审批状态，不无限等待。
- Web 显示对应工具的开始与结束状态，与原生记录一致；不以状态动画或模拟结果代替实际执行。
- 运行中和未解决审批期间不会自动释放；完成后按配置释放，列表读取不续期。
- 用户手动归还能够确认退出，或给出明确且可恢复的失败状态；不会遗留无法辨认的 writer。
- 原生客户端可接回同一测试对话；Web 读取不会自动抢回，重启不会自动重放已归还任务。
- 既有回归与原生会话交接测试通过；未改变其他任务、审批策略或 SSL 配置。
