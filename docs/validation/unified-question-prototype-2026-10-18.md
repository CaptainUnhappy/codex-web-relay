# 统一提问服务隔离原型验收

日期：2026-10-18，Asia/Taipei。分支：`codex/unified-question-prototype`。

本记录保留第一阶段的范围与证据。后续已完成的真实 MCP/App 隔离验收另见 [工具接入记录](unified-question-app-tool-2026-10-18.md)，不将后续能力回填为第一阶段已经验证。

## 结论与范围

隔离原型通过：手机模拟视口与桌面浏览器共享一个问题状态；任一端回答后，两端关闭回答控件并显示同一份答案。同题并发提交、双击、重复请求、成功响应丢失、断线重连和服务进程重启均没有增加第二份答案。

这不是 Codex App 原生卡片的完成验收。桌面端是独立卡片页面，手机端为 Chromium 移动视口及触摸模拟；未接入真实模型、真实 Codex 会话、MCP 注册或公网中继。正式服务与启动配置没有切换。

代码：[原型与运行说明](../../lib/question-service-prototype/README.md)。一条启动命令：`npm.cmd run prototype:questions`。本次使用 Node.js 24.19.0 和其内置 SQLite 3.53.3，没有增加 npm 依赖。

## 设计决策与根因对应

原问题允许普通聊天消息绕过 App 的问题确认状态。原型建立单一问题记录：调用方创建稳定问题 ID；服务端以该 ID 原子保存答案及确认事件；两端只根据服务端已确认记录关闭入口。

`answers.question_id` 主键和写事务共同拒绝第二份答案。`requestId` 用于识别同一提交的重试，`receiptId` 用于返回稳定确认结果。接受消息和界面关闭不再依赖各端自己的“发送成功”判断。

前台每秒读取一致快照，后台暂停；恢复可见或网络恢复后读取完整状态。当前原型不需要接管 Codex session，也没有维持 WebSocket 长连接。已确认的版本不会被较旧或相同版本的返回覆盖。

## 实际校验结果

### 服务与持久化

执行 `npm.cmd run prototype:questions:check`，退出码 0：

| 场景 | 断言结果 |
| --- | --- |
| 20 个不同请求同时回答同一题 | 1 个 accepted，19 个 409 |
| 同一请求编号重复发送 | 返回原收据，revision 不增加 |
| 同一编号换答案 | `REQUEST_ID_REUSED`，不覆盖原答案 |
| 重复建题与读取 | 相同建题复用原记录；只读不确认问题 |
| 答案插入后、事件写入时注入失败 | 整个事务回滚，答案仍为空；恢复后同编号可成功一次 |
| 两个独立 Node 进程共用 SQLite | 仅一个进程接受答案 |
| 关闭、重开服务及数据库 | 原答案和收据完整保留，重试仍为 duplicate |
| 调用方等待回答 | 单次调用只返回一份 canonical result |
| 未认证、跨来源、非法输入 | 分别被拒绝 |

本项最终为 4 题、4 条答案、4 次确认事件，`PRAGMA integrity_check=ok`。

### 双端真实 HTTP 浏览器流程

执行 `browser-check.js`，主实现完成后通过一次，快照去重及输入框调整后又完整通过一次。两端为独立 Chromium context，手机 390×844 / 320×700、触摸模式，桌面 1280×900。

| 场景 | 实测结果 |
| --- | --- |
| 手机选择选项并改为自定义文本后发送 | 两端回答控件关闭，换行和 `<beta>` 完整保留 |
| 桌面键盘选择并发送 | 手机同步关闭，结果相同 |
| 双端同时提交不同答案 | 实际请求屏障同时放行；HTTP 200/409 各一次，两端显示获胜答案 |
| 同编号重试、换内容重试 | 原收据复用；修改被拒绝，事件数不增加 |
| 双击发送 | 仅产生一个 POST |
| 手机断网，桌面回答 | 手机重连后恢复已答状态，没有自动发送；未发草稿保留 |
| 请求到达服务前中断 | 服务保持待答；刷新后重试沿用原 requestId，仅保存一次 |
| 服务提交成功，网络响应被丢弃 | 两端通过只读查询恢复；总共只有一次 POST |
| 旧 GET 响应晚于成功 POST 到达 | 已答卡片未重新打开 |
| 收起、刷新、重新打开 | 未发送内容保留，可以继续回答 |
| 长文本、换行、HTML 字符 | 正常换行、不执行 HTML、320px 无横向溢出 |

最终 9 个问题、9 个不同的答案收据、revision 18（9 次创建＋9 次回答），原型页面 `pageerror=0`。正常数据请求连接真实 HTTP 服务和 SQLite；只对明确的故障场景拦截网络，没有用 mock 答案替代服务端确认。

消费者也是真实独立 Node 子进程执行 `ask.js`：`consumer-result.json` 中 `code=0`、`lines` 长度为 1，包含手机提交的多行文本与服务端收据。它没有调用真实模型。

### 进程重启与落盘复查

第一轮浏览器测试后保留两个页面，停止测试服务，实际观察到两端显示“连接已中断”，9 条已答状态仍在。以原端口、原数据目录恢复测试服务，两端自动变为“已连接”；再次刷新仍有 9 条答案。直接查询数据库得到：

```json
{"questions":9,"answers":9,"answerEvents":9,"integrity":"ok"}
```

两轮测试数据目录分别为 `output/question-prototype/PROTOTYPE-ZqQi1p` 与 `PROTOTYPE-ycLgpx`。它们是忽略的实验数据，可用于本地复查。测试进程及浏览器 context 在验收后关闭；常规预览另用 18789 端口和随机密钥。

## 独立审查处理

分别审查了存储/消费者与 UI/故障测试。补上了相同 revision 快照的忽略处理。审查指出固定测试密钥只适用于 fixture：它只能访问本机合成测试数据，验收后停止；常规启动使用随机密钥。未将此测试入口作为生产身份认证方案。

Home/End 键与大规模历史分页未纳入原型。方向键、Enter/Space、触摸、焦点、选中状态和基本文本可访问性已覆盖。
