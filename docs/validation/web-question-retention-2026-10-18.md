## 本次反馈的实际原因

用户截图中的“Web 提问卡片复验”已有 `WEB_QUESTION_CARD_OK` 回显。这条回答由上一轮端到端测试提交，用户本人没有操作。Mini 按持久记录中的回答关联将其判为已回答，所以返回会话时不再显示该问题；截图中的 Codex App 仍显示旧卡片，不能据此认为模型尚未收到回答。

当时查询该测试对话的 `/codex/approvals` 返回 0 条问题。当前可控制的 Web 页面中，`renderApproval` 不包含新展开选项代码，`renderQuestionReply` 尚不存在，说明该打开页面仍保留旧前端脚本；截图中的旧式“Codex 提问／你的回答”气泡也与之相符。

上一轮验证确实证明了发送与回显，但没有证明 App 卡片关闭状态与 Web 一致。本次不把已回答问题重新开放，以免造成重复提交，也不声称解决了 App 内部关闭状态同步。

## 后续计划：跨客户端关闭状态一致性

当前证据只证明 App 截图仍显示已通过 Web 提交的问题，尚未找到 App 提问 UI 关闭状态的公开读写接口。

目标：识别 App 和 Mini 可共同依赖的问题状态，避免一端显示待回答、另一端已完成的误解。

1. 在新的隔离问题中分别从 App、Web 提交一次，对照原生消息、问题标识和可用协议事件；避免重复发送同一个答案。
2. 查明 App 是否提供受支持的回答确认或关闭通知；不修改 App 私有数据库，不写 rollout，不用关闭整个 App 强行刷新。
3. 若存在受支持接口，补齐同步并测试两端重开；若不存在，明确显示“已在另一端回答”，保留回答历史与可审查的状态来源，不重开可发送表单。

验收：单次回答只送达一次；状态证据可追溯；两端刷新后无误导性待答状态；读取与切换不接管会话。该后续计划尚未开始实现。
